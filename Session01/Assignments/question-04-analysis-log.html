لاگ مسیر تحلیل سؤال چهارم

این فایل مسیر پرسش‌ها، پاسخ‌ها و تحلیل‌هایی را ثبت می‌کند که به پاسخ نهایی سؤال چهارم می‌رسند.

موضوع: Dependency، Parallelism، Analyze و معنای واقعی پوشش Requirementها توسط Tasks

صورت سؤال

برای یک Feature، تعداد ۳۰ Task تولید شده و هر Requirement حداقل به یک Task مرتبط است. با این حال:

  • یک Task به دیتابیس آماده نیاز دارد، در حالی که Migration دیتابیس در Task بعدی تعریف شده است.
  • دو Task دارای نشانگر [P] باید فایل مشترکی را تغییر دهند.
  1. چه مشکلاتی در Dependency و Parallelism وجود دارد؟
  2. انتظار دارید Analyze چه Findingهایی گزارش کند؟
  3. آیا پوشش ۱۰۰٪ Requirementها توسط Tasks، آمادگی قطعی برای Implement را ثابت می‌کند؟ چرا؟

مسیر گفت‌وگو

درخواست کاربر: شروع سؤال چهارم

«بریم سؤال چهارم»

آماده‌سازی مفهومی: دو اصطلاح لازم

  • Dependency: اگر Task «ب» برای شروع یا تکمیل به خروجی Task «الف» نیاز داشته باشد، «ب» به «الف» وابسته است و «الف» باید زودتر انجام شود.
  • [P] یا Parallel: یعنی Task می‌تواند هم‌زمان با Taskهای موازی دیگر اجرا شود، چون وابستگی اجرایی و محل تغییر متداخل با آن‌ها ندارد.
  • Analyze: اسناد Specification، Plan و Tasks را بدون پیاده‌سازی با هم مقایسه می‌کند تا ناسازگاری، ابهام، نقص پوشش، ترتیب نادرست و ادعای موازی‌بودن نامعتبر را پیدا کند.

پرسش‌های دور اول

  1. فرض کن T12 باید داده‌ای را در جدول Requests ذخیره کند و T13 تازه آن جدول را با Migration می‌سازد. ترتیب درست این دو چیست و اگر ترتیب فعلی حفظ شود چه اتفاقی ممکن است بیفتد؟
  2. دو Task با نشانگر [P] هم‌زمان یک فایل مشترک را ویرایش می‌کنند. آیا واقعاً مستقل و قابل اجرای موازی‌اند؟ یک خطر مشخصِ این کار را نام ببر.
  3. فرض کن هر Requirement به یک Task لینک شده است، اما یکی از Taskها ناقص، مبهم یا در ترتیب نامناسب قرار دارد. آیا عدد «پوشش ۱۰۰٪» به‌تنهایی اجازه می‌دهد Implement را با اطمینان شروع کنیم؟ دلیل پاسخ را با یک مثال کوتاه بگو.

پاسخ کاربر — دور اول

  1. ترتیب فعلی شدنی نیست، چون در ابتدا جدول وجود ندارد. Analyze احتمالاً موضوع را تشخیص می‌دهد، سپس ابتدا T13 را به‌عنوان پیش‌نیاز T12 و بعد T12 را اجرا می‌کند.
  2. خیر؛ به‌نظر کاربر اصولاً نباید بیش از یک Task روی یک فایل اجرا شود، چون به تداخل می‌خورند.
  3. خیر؛ ابتدا باید Clarification به‌درستی انجام شود.

بازخورد و اصلاح مفهومی

  1. تشخیص وابستگی درست است، اما Analyze اجرا نمی‌کند. Analyze یک بررسی غیرمخرب است: گزارش می‌دهد که T12 به خروجی T13 نیاز دارد و ترتیب یا Dependency ثبت‌شده نادرست است. سپس باید تعریف Tasks اصلاح شود تا Migration قبل از Task وابسته قرار گیرد؛ اجرای آن‌ها وظیفهٔ مرحلهٔ Implement است.
  2. ممنوعیت مطلق لازم نیست. چند Task می‌توانند در زمان‌های متفاوت یک فایل را ویرایش کنند. مشکل این سناریو آن است که دو Task با برچسب [P] قرار است هم‌زمان همان فایل را تغییر دهند؛ بنابراین مستقل نیستند و خطر Conflict، بازنویسی تغییرات یکدیگر یا تولید کد ناسازگار وجود دارد. راه معمول، حذف [P] و تعیین ترتیب یا بازطراحی مرز Taskهاست.
  3. Clarify تنها درمان ممکن نیست. اگر خود Requirement مبهم باشد، Clarify لازم است؛ اما اگر Requirement روشن و Task ناقص یا بدترتیب باشد، اشکال در Tasks/Plan است و باید همان‌جا اصلاح شود. پوشش ۱۰۰٪ فقط می‌گوید برای هر Requirement یک لینک وجود دارد، نه اینکه Task مرتبط کافی، صحیح، مستقل، آزمون‌پذیر یا دارای ترتیب درست است.

پرسش‌های دور دوم

  1. با توجه به اینکه Analyze غیرمخرب است، انتظار داری برای وابستگی T12 و T13 چه Finding مشخصی بنویسد و بعد از آن چه چیزی در فایل Tasks اصلاح شود؟
  2. اگر T20 امروز بخشی از یک فایل را بسازد و T21 بعد از تکمیل آن، فردا همان فایل را توسعه دهد، آیا اصلِ اشتراک فایل مشکل است یا فقط ادعای اجرای موازی؟
  3. کدام مورد به Clarify نیاز دارد و کدام مورد به اصلاح Tasks؟
    • Requirement می‌گوید «مدیر درخواست را تأیید می‌کند»، اما معلوم نیست کدام مدیر مجاز است.
    • Requirement کاملاً روشن است، اما Migration بعد از Task وابسته آمده است.

پاسخ کاربر — دور دوم

  1. کاربر هنوز معنای دقیق Finding را نمی‌داند، اما معتقد است باید برای T12 پیش‌نیاز بودن T13 مشخص شود.
  2. در حالت اجرای ترتیبی، اشتراک فایل مشکل نیست و فقط ادعای اجرای موازی نادرست است.
  3. ابهام دربارهٔ مدیر مجاز به Clarify و ترتیب نادرست Migration به اصلاح Tasks نیاز دارد.

آموزش: Finding دقیقاً چیست؟

Finding یعنی «مورد یا ایرادی که در بررسی پیدا و گزارش شده است». Finding خودِ اصلاح نیست؛ شرح مستندِ مشکلی است که به ما می‌گوید چه چیزی، کجا و چرا ناسازگار یا پرخطر است.

یک Finding معمولاً می‌تواند این اجزا را داشته باشد:

  • دسته: مثلاً Dependency یا Parallelism
  • محل: Taskهای درگیر، مانند T12 و T13
  • شرح مشکل: چه ناسازگاری‌ای مشاهده شده است
  • اثر یا شدت: چرا می‌تواند اجرای کار را مختل کند
  • پیشنهاد اصلاح: چه تغییری مشکل را برطرف می‌کند
نمونهٔ Finding وابستگی:
T12 از جدول Requests استفاده می‌کند، اما Migration سازندهٔ آن در T13 و بعد از Task مصرف‌کننده قرار گرفته است. در صورت اجرای ترتیب فعلی، T12 ممکن است شکست بخورد. T13 را پیش از T12 قرار دهید و وابستگی T12 → T13 را ثبت کنید.

پس عبارت بدون ابهام این است: T13 پیش‌نیاز T12 است؛ یا T12 به T13 وابسته است.

پاسخ‌های دوم و سوم کاربر درست‌اند: ویرایش ترتیبی یک فایل ذاتاً مشکل ندارد و ابهام Requirement با Clarify حل می‌شود، درحالی‌که ترتیب غلط Taskها باید در خود Tasks اصلاح شود.

پرسش‌های جمع‌بندی

  1. برای دو Task موازی که فایل مشترک دارند، Finding را در یک جمله و پیشنهاد اصلاحش را در یک جملهٔ جدا بنویس.
  2. پوشش ۱۰۰٪ فقط چه چیزی را ثابت می‌کند؟ علاوه بر Coverage، دو نمونه از چیزهایی را نام ببر که برای آمادگی Implement باید بررسی شوند.

پاسخ کاربر — جمع‌بندی

  1. Task پیش‌نیاز شناسایی و با اولویت اول انجام شود؛ تا زمان تأیید یا Pass شدن تست‌ها، Task بعدی اجازهٔ اجرا نداشته باشد.
  2. پوشش ۱۰۰٪ فقط ثابت می‌کند به‌ازای هر Requirement یک Task وجود دارد؛ اما شفاف‌بودن، قابل‌پیاده‌سازی‌بودن و ترتیب مناسب آن Task را ثابت نمی‌کند.

اصلاح نهایی: Dependency در برابر تداخل اجرای موازی

پاسخ دوم کامل و درست است. پاسخ اول راه‌حل یک Dependency واقعی را توصیف می‌کند، اما در سناریوی فایل مشترک لزوماً هیچ‌یک از دو Task از نظر منطقی به خروجی دیگری نیاز ندارد. مشکل این است که آن‌ها یک منبع مشترک—فایل—را هم‌زمان تغییر می‌دهند و بنابراین ادعای [P] معتبر نیست.

Finding: دو Task با نشانگر [P] فایل مشترکی را تغییر می‌دهند؛ پس اجرای هم‌زمان آن‌ها ممکن است Conflict، بازنویسی تغییرات یا کد ناسازگار ایجاد کند.
پیشنهاد اصلاح: نشانگر [P] از یکی یا هر دو حذف و ترتیب اجرای آن‌ها مشخص شود؛ یا مرز Taskها و فایل‌ها طوری بازطراحی شود که تغییرات واقعاً مستقل شوند.

«تأیید» یا «Pass شدن تست‌ها» شرطی اضافی است که صورت سؤال تعیین نکرده است. برای جلوگیری از تداخل، کافی است Task دوم پس از پایان Task اول شروع شود؛ مگر اینکه Definition of Done پروژه صراحتاً تکمیل Task را به تست یا تأیید وابسته کرده باشد.

آخرین بررسی

تفاوت این دو را با یک جمله برای هرکدام بیان کن:

  1. Dependency: چرا T12 بدون T13 نمی‌تواند کار کند؟
  2. Parallelism conflict: چرا دو Taskِ فاقد وابستگی منطقی ممکن است باز هم نتوانند هم‌زمان اجرا شوند؟

پاسخ کاربر — آخرین بررسی

  1. T13 پیش‌نیاز T12 است.
  2. بخشی از یک پیاده‌سازی ممکن است بر بخش دیگر اثر بگذارد و کار دو Task در نقطه‌ای مشترک شود.

صورت‌بندی دقیق پاسخ

  1. Dependency: T13 جدول موردنیاز را ایجاد می‌کند و T12 بدون وجود آن جدول قادر به انجام کارش نیست؛ بنابراین T13 پیش‌نیاز واقعی T12 است.
  2. Parallelism conflict: دو Task ممکن است برای تحقق هدف خود به خروجی یکدیگر نیاز نداشته باشند، اما چون منبع مشترکی مانند یک فایل را تغییر می‌دهند، اجرای هم‌زمانشان می‌تواند باعث تداخل یا ازبین‌رفتن تغییرات شود. پس عدم وجود Dependency به‌تنهایی Parallel بودن را ثابت نمی‌کند.

نکتهٔ مهم در پاسخ اول این است که «پیش‌نیاز بودن» نتیجه است؛ علت فنی باید نیز گفته شود: T13 چیزی را می‌سازد که T12 مصرف می‌کند.

تحلیل نهایی

۱. مشکل Dependency

Task مصرف‌کنندهٔ دیتابیس پیش از Migration قرار گرفته است. این ترتیب معتبر نیست، زیرا Task مصرف‌کننده به ساختار دیتابیسی نیاز دارد که هنوز ایجاد نشده است. اگر T13 Migration را ایجاد می‌کند و T12 از جدول حاصل استفاده می‌کند، رابطهٔ صحیح چنین است:

T13 پیش‌نیاز T12 است؛ یا T12 به T13 وابسته است.

پس باید Migration پیش از Task وابسته قرار گیرد و این رابطه در ترتیب یا Dependencyهای Tasks ثبت شود. Analyze این ناسازگاری را گزارش می‌کند، اما Taskها را اجرا یا خودکار جابه‌جا نمی‌کند؛ اجرای ترتیب اصلاح‌شده متعلق به مرحلهٔ Implement است.

۲. مشکل Parallelism

دو Task دارای نشانگر [P] باید مستقل و برای اجرای هم‌زمان امن باشند. اگر هر دو فایل مشترکی را تغییر دهند، این ادعا معتبر نیست؛ زیرا ممکن است Conflict، بازنویسی تغییرات یکدیگر یا کد ناسازگار ایجاد شود.

این وضعیت الزاماً به معنی وجود Dependency منطقی میان دو Task نیست. ممکن است هیچ‌کدام به خروجی دیگری نیاز نداشته باشد، اما به‌دلیل تغییر یک منبع مشترک نتوانند هم‌زمان اجرا شوند. راه اصلاح یکی از این دو است:

  • حذف نشانگر [P] و تعیین ترتیب اجرای Taskها؛
  • بازطراحی مرز Taskها یا فایل‌ها به‌گونه‌ای که تغییرات واقعاً مستقل شوند.

۳. Findingهای مورد انتظار از Analyze

Finding یعنی ایراد یا ناسازگاری مستندی که در بررسی کشف می‌شود، نه خودِ اجرای اصلاح. انتظار می‌رود Analyze دست‌کم این موارد را گزارش کند:

  1. Dependency/Ordering Finding: Task وابسته به دیتابیس پیش از Migration قرار گرفته و در ترتیب فعلی ممکن است شکست بخورد.
  2. Parallelism Finding: دو Task با نشانگر [P] فایل مشترکی را تغییر می‌دهند و بنابراین برای اجرای موازی امن نیستند.

هر Finding مناسب باید محل مشکل، شرح ناسازگاری، اثر احتمالی و پیشنهاد اصلاح را روشن کند.

۴. آیا Coverage صددرصد آمادگی Implement را ثابت می‌کند؟

خیر. پوشش ۱۰۰٪ فقط ثابت می‌کند که برای هر Requirement دست‌کم یک Task مرتبط ثبت شده است. این معیار، وجود رابطه را می‌سنجد؛ نه کیفیت و کفایت آن را.

پیش از Implement باید بررسی شود که Taskها:

  • شفاف، دقیق و قابل پیاده‌سازی باشند؛
  • تمام رفتار و محدودیت Requirement را واقعاً پوشش دهند؛
  • ترتیب و Dependencyهای صحیح داشته باشند؛
  • برچسب‌های Parallel معتبر داشته باشند و بر سر فایل یا منبع مشترک تعارض نکنند؛
  • با Specification و Plan ناسازگار نباشند.

اگر خود Requirement مبهم باشد، Clarify لازم است؛ اما اگر Requirement روشن و Task ناقص، متعارض یا بدترتیب باشد، باید Plan یا Tasks اصلاح شود.

نتیجهٔ نهایی

Traceability یا پوشش Requirementها شرط لازم است، اما شرط کافی برای شروع Implement نیست. آمادگی واقعی زمانی به دست می‌آید که علاوه بر Coverage، کیفیت Taskها، ترتیب وابستگی‌ها و ایمنی اجرای موازی نیز بررسی و اصلاح شده باشند.
