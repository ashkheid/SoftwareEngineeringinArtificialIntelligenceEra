# پاسخ سؤالات تشریحی — جلسهٔ اول

## سؤال ۱ — Constitution و حاکمیت معماری

### تحلیل نهایی

موفق‌شدن Testها و رعایت معماری دو نوع اطمینان متفاوت ایجاد می‌کنند. Testهای رفتاری نشان می‌دهند
سیستم در سناریوهای آزموده‌شده خروجی مورد انتظار را تولید می‌کند؛ اما لزوماً بررسی نمی‌کنند این
رفتار در کدام لایه پیاده‌سازی شده است. بنابراین ممکن است Controller شامل تمام بررسی‌های وضعیت،
مجوز و Self-Approval باشد و Testهای HTTP همچنان موفق شوند. در چنین حالتی رفتار فعلی درست است،
ولی ساختار سیستم با تصمیم معماری تیم سازگار نیست.

این تفاوت در توسعه‌های بعدی اهمیت بیشتری پیدا می‌کند. اگر قاعدهٔ «هیچ‌کس نباید درخواست خودش را
تأیید کند» فقط داخل Controller قرار بگیرد، مسیری مانند Background Job، CLI یا Message Queue
می‌تواند Controller را دور بزند و آن قاعده را اجرا نکند. محل مناسب اجرای چنین قواعدی
Application یا Domain است تا رفتار کسب‌وکار مستقل از روش ورود درخواست باقی بماند. Controller
باید فقط جزئیات HTTP را مدیریت کند: ورودی را بخواند، Use Case را فراخوانی کند و نتیجهٔ مستقل از
HTTP را به Response مناسب، مانند `409 Conflict`، تبدیل کند.

#### محل ثبت قاعدهٔ معماری

قاعدهٔ «Business Logic باید در Application یا Domain قرار بگیرد و API فقط مسئول دریافت درخواست
و ارائهٔ پاسخ باشد» یک اصل پایدار و سراسری معماری است؛ بنابراین مرجع اصلی و الزام‌آور آن باید
Constitution باشد. بااین‌حال، ثبت آن در Constitution به این معنا نیست که Plan و Tasks نقشی
ندارند:

- **Constitution** اصل غیرقابل‌چشم‌پوشی و معیار ارزیابی تصمیم‌ها را تعریف می‌کند.
- **Plan** نشان می‌دهد Feature مشخص چگونه با ساختار لایه‌ها، جهت وابستگی‌ها و Use Caseها این
  اصل را رعایت می‌کند.
- **Tasks** طراحی را به کارهای اجرایی و قابل پیگیری، مانند ایجاد Use Case و نازک نگه‌داشتن
  Controller، تبدیل می‌کند.

پس این سه Artifact جایگزین یکدیگر نیستند؛ یک قانون واحد را در سه سطح «حاکمیت»، «طراحی» و «اجرا»
قابل ردیابی می‌کنند.

#### جلوگیری از تکرار مشکل

برای جلوگیری از تکرار این تخلف، اتکا به مستندات به‌تنهایی کافی نیست و باید چند لایهٔ مکمل وجود
داشته باشد:

1. اصل جداسازی مسئولیت‌ها به‌صورت صریح و قابل ارزیابی در Constitution ثبت شود.
2. Plan هر Feature محل اجرای قواعد کسب‌وکار و مرز لایه‌های درگیر را مشخص کند.
3. Tasks شامل کارهای صریح برای Application/Domain، Controller و آزمون‌های مربوط به آن‌ها باشد.
4. Architecture Test یا قوانین وابستگی در CI، وابستگی‌های ممنوع میان لایه‌ها را شناسایی کنند.
5. Code Review با Checklist بررسی کند که Controller فقط کارهای مربوط به HTTP، فراخوانی
   Application و نگاشت نتیجه را انجام می‌دهد.

Architecture Test می‌تواند بخشی از تخلف‌ها، مانند وابستگی Domain به API یا Infrastructure، را
خودکار تشخیص دهد؛ ولی همیشه قادر نیست معنای یک شرط داخل Controller را بفهمد. به همین دلیل کنترل
خودکار باید با بازبینی انسانی تکمیل شود.

**نتیجه:** سبزبودن Testها برای اعلام صحت رفتار لازم است، اما برای اعلام انطباق کامل کافی نیست.
قابلیت زمانی با تصمیم تیم سازگار است که علاوه بر رفتار صحیح، قواعد Constitution، طراحی ثبت‌شده
در Plan و مرزهای مسئولیتی نیز رعایت شده باشند.

## سؤال ۲ — Specify و Clarify

### تحلیل نهایی

#### ۱. آیا Agent مجاز است Self-Approval را بدون تأیید مالک محصول نهایی کند؟

خیر. مجازبودن یا ممنوع‌بودن Self-Approval یک جزئیات فنی نیست؛ یک سیاست کسب‌وکار دربارهٔ تفکیک
وظایف، تعارض منافع و میزان اعتماد به فرایند تأیید است. Agent می‌تواند گزینه‌ها و پیامدهایشان را
تحلیل یا یک گزینه را پیشنهاد کند، اما دانش قطعی از سیاست سازمان و اختیار نهایی‌کردن آن را
ندارد.

اگر Agent خودسرانه Self-Approval را مجاز کند، معنای «تأیید» از بررسی توسط یک مرجع مستقل به
تأیید شخص بر درخواست خودش تغییر می‌کند. این کار می‌تواند یکپارچگی و قابلیت اعتماد فرایند را از
بین ببرد. تا زمان پاسخ مالک محصول، این مورد باید به‌عنوان ابهام حل‌نشده ثبت شود و فقط بخش
وابسته به آن نهایی نشود؛ بخش‌های مستقل می‌توانند ادامه پیدا کنند.

#### ۲. تفاوت Assumption با تصمیم تأییدشدهٔ مالک محصول

**Assumption** گزاره‌ای موقت و تأییدنشده است که ممکن است از Context به‌شکل معقول استنباط شده
باشد و برای تحلیل یا پیشبرد محدود کار استفاده شود. Assumption باید آشکارا ثبت شود، مرجع نهایی
نیست، قابل بازگشت است و نباید یک سیاست پراثر کسب‌وکار را پنهانی قطعی کند.

**تصمیم تأییدشده** توسط مرجع صاحب اختیار—در اینجا مالک محصول—اتخاذ یا تأیید شده است. این تصمیم
در Specification ثبت می‌شود و تا زمانی که رسماً تغییر نکند، مبنای طراحی، پیاده‌سازی و پذیرش
محصول است.

#### ۳. ابهام‌های مهم دیگر

- **تعریف نقش مدیر:** چه کسی مدیر محسوب می‌شود و چه شاخص‌هایی او را واجد صلاحیت بررسی می‌کند؟
- **دامنهٔ اختیار:** هر مدیر درخواست کدام افراد، تیم‌ها یا واحدها را می‌تواند تأیید کند؟
- **دامنهٔ مشاهده:** هر مدیر کدام درخواست‌ها را می‌تواند ببیند؟ آیا فقط درخواست‌های تیم خودش یا
  همهٔ سازمان؟
- **معیارهای تأیید:** برای تأیید یک درخواست چه اطلاعات، کنترل‌ها یا شرایطی باید کامل باشند؟

تعریف مدیر، دامنهٔ مشاهده و دامنهٔ اختیار سه موضوع مستقل‌اند. ممکن است مدیری درخواست را ببیند،
اما مجاز به تأیید آن نباشد. ترتیب Clarifyکردن آن‌ها باید بر پایهٔ ریسک و اثر باشد؛
Self-Approval اولویت بالایی دارد و در نبود نگرانی ویژهٔ محرمانگی، دامنهٔ اختیار تأیید معمولاً
پیش از دامنهٔ مشاهده بررسی می‌شود.

#### ۴. نقش Specify و Clarify

**Specify** دانسته‌ها، رفتار مورد انتظار، محدودیت‌ها، Assumptionها و نقاط مبهم را به‌شکل منظم
در Specification ثبت می‌کند. وظیفهٔ آن پنهان‌کردن ابهام یا اختراع پاسخ نیست؛ ابهام‌های پراثر
مانند Self-Approval، تعریف مدیر، دامنهٔ دسترسی و معیارهای تأیید باید در آن برجسته شوند.

**Clarify** ابهام‌های مهم را بر اساس اثر و ریسک اولویت‌بندی می‌کند، سؤال‌های هدفمند را از مرجع
صاحب اختیار می‌پرسد و پاسخ‌ها را به Specification بازمی‌گرداند. جواب نباید فقط در تاریخچهٔ
گفتگو باقی بماند؛ باید به Requirement روشن و قابل آزمون تبدیل شود.

برای نمونه، پس از تأیید مالک محصول می‌توان نوشت: **«سیستم باید هر تلاش برای تأیید درخواست توسط
ثبت‌کنندهٔ همان درخواست را رد کند، حتی اگر ثبت‌کننده نقش مدیر داشته باشد.»** این عبارت مشخص
می‌کند چه رفتاری لازم است و می‌توان برای آن آزمون پذیرش نوشت.

#### نتیجه

Agent در مواجهه با ابهام پراثر باید آن را آشکار و قابل پیگیری کند، نه اینکه برداشت خود را جای
تصمیم مالک محصول بنشاند. Specify محل صورت‌بندی مسئله و برجسته‌کردن ابهام‌هاست؛ Clarify فرایند
حل هدفمند آن‌ها و تبدیل پاسخ‌های تأییدشده به نیازمندی‌های قابل آزمون است.

## سؤال ۳ — Requirement در برابر Design Decision

### تحلیل نهایی

#### ۱. Requirement در برابر Design Decision

این گزاره یک Requirement است:

> «هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده، بدون بررسی و تأیید معتبرِ آن محتوا، اجرا
> شود.»

این گزاره نتیجه و محدودیتی قابل مشاهده را تعریف می‌کند که سیستم باید مستقل از روش پیاده‌سازی
تضمین کند. در مقابل، افزودن فیلد عددی `ContentRevision` یک Design Decision است؛ زیرا فقط یکی از
راه‌های ممکن برای تشخیص متفاوت‌بودن نسخهٔ فعلی و نسخهٔ تأییدشده است.

صرف وجود `ContentRevision` Requirement را برآورده نمی‌کند. سیستم باید علاوه بر تشخیص اختلاف
نسخه، از اجرای نسخهٔ فاقد تأیید معتبر نیز جلوگیری کند:

- **Detection:** تشخیص اینکه محتوای فعلی همان محتوای تأییدشده نیست.
- **Enforcement:** متوقف‌کردن اجرا و الزام به بررسی و تأیید نسخهٔ جدید.

#### ۲. چرا مکانیزم فنی باید در Plan/Research بررسی شود؟

اگر Specification از ابتدا استفاده از `ContentRevision` را اجباری کند، پیش از بررسی گزینه‌ها،
مدل داده، API و تمام مسیرهای ویرایش به یک راهکار خاص مقید می‌شوند. در Plan/Research می‌توان
گزینه‌ها را بر اساس نیاز واقعی و معیارهایی مانند قابلیت Audit، نمایش Diff، هزینهٔ ذخیره‌سازی،
پیچیدگی Query، هم‌زمانی و امنیت مقایسه کرد.

قاعدهٔ «Specification چه و Plan چگونه» راهنمای مفیدی است، اما مطلق نیست. اگر یک محدودیت فنی
خودش نیازی واقعی و تأییدشده، مانند الزام قانونی یا سازگاری اجباری باشد، می‌تواند در
Specification قرار گیرد. در این مسئله دلیلی وجود ندارد که فیلد `ContentRevision` خودش یک نیاز
کسب‌وکار باشد.

#### ۳. راهکارهای جایگزین و Trade-offها

#### Snapshot محتوای تأییدشده

هنگام تأیید، یک کپی از محتوای درخواست ذخیره می‌شود. سپس می‌توان Snapshot را با محتوای فعلی
مقایسه کرد.

- **مزایا:** محتوای دقیق تأییدشده برای Audit در دسترس است و با یک مقایسه‌گر می‌توان جزئیات
  تغییرات را نمایش داد.
- **معایب:** فضای بیشتری مصرف می‌کند، داده ممکن است تکرار شود و نگهداری چند کپی از دادهٔ حساس
  ملاحظات بیشتری ایجاد می‌کند.

#### Hash محتوای تأییدشده

در زمان تأیید، اثر انگشت محتوا ذخیره و پیش از اجرا با Hash محتوای فعلی مقایسه می‌شود.

- **مزایا:** کوچک و سریع است و بدون نگهداری یک کپی کامل، برابری یا نابرابری محتوا را تشخیص
  می‌دهد.
- **معایب:** نشان نمی‌دهد چه چیزی تغییر کرده و به قالب‌بندی Canonical و الگوریتم مناسب نیاز
  دارد. Hash معمولی به‌تنهایی هویت، Authorization یا اصالت تغییر را اثبات نمی‌کند.

#### Immutable Versions

هر ویرایش به‌جای بازنویسی دادهٔ قبلی، نسخهٔ جدیدی می‌سازد. برای نمونه، تأیید
`Request-42 / Version-1` فقط به همان نسخه متصل است و `Version-2` باید تأیید مستقل دریافت کند.

- **مزایا:** تاریخچه، محتوای هر نسخه و مرز اعتبار تأیید روشن و قابل Audit باقی می‌ماند.
- **معایب:** ذخیره‌سازی، Queryها و مدیریت چرخهٔ عمر نسخه‌ها پیچیده‌تر می‌شوند.

#### ۴. جایگاه PRD و ADR

- **PRD:** مسئلهٔ محصول، ارزش مورد انتظار، کاربران، محدوده و معیار موفقیت را بیان می‌کند. این
  Requirement می‌تواند ابتدا از PRD آمده باشد.
- **Specification:** نیاز را به رفتار روشن و آزمون‌پذیر سیستم تبدیل می‌کند.
- **Plan/Research:** گزینه‌های پیاده‌سازی را بررسی و راهکار مناسب را طراحی می‌کند.
- **ADR:** اگر انتخاب راهکار یک تصمیم معماری مهم و بلندمدت باشد، زمینه، گزینه‌ها، تصمیم، دلایل
  و پیامدهای آن را ثبت می‌کند.

هر تصمیم فنی کوچک به ADR نیاز ندارد. انتخابی مانند Immutable Versions فقط زمانی شایستهٔ ADR است
که اثر معماری معناداری داشته باشد.

#### ۵. ارتباط با تعریف مدیر و اعتبار تأیید

سؤال دوم مشخص می‌کرد چه کسی مجاز به مشاهده یا تأیید درخواست است؛ سؤال سوم مشخص می‌کند تأیید به
کدام محتوای دقیق تعلق دارد. هر دو برای اعتبار کامل لازم‌اند:

1. **اعتبار تأییدکننده:** فرد نقش و محدودهٔ اختیار مناسب داشته باشد، درخواست در حوزهٔ او قرار
   گیرد و قواعدی مانند منع Self-Approval رعایت شوند.
2. **اعتبار محتوا:** نسخهٔ در حال اجرا دقیقاً همان نسخهٔ بررسی و تأییدشده باشد.

Visibility با Approval Authority یکسان نیست؛ ممکن است مدیری درخواستی را ببیند اما حق تأیید آن
را نداشته باشد. بنابراین یک تأیید قابل ردیابی باید دست‌کم هویت تأییدکننده، محدودهٔ اختیار، زمان
تأیید و نسخهٔ دقیق محتوای تأییدشده را به هم متصل کند.

#### نتیجه

Requirement باید تضمین کسب‌وکار را بدون قفل‌کردن زودهنگام راه‌حل بیان کند. سپس Plan/Research
گزینه‌های فنی را با Trade-offهایشان می‌سنجد و در صورت معماری‌بودن تصمیم، نتیجه در ADR ثبت
می‌شود. در این مسئله، موفقیت زمانی حاصل شده است که سیستم هم تغییر محتوا را تشخیص دهد، هم اجرای
نسخهٔ تأییدنشده را متوقف کند، و هم اعتبار تأییدکننده و محدودهٔ اختیار او را رعایت کند.

## سؤال ۴ — Tasks و Analyze

### تحلیل نهایی

#### ۱. مشکل Dependency

Task مصرف‌کنندهٔ دیتابیس پیش از Migration قرار گرفته است. این ترتیب معتبر نیست، زیرا Task
مصرف‌کننده به ساختار دیتابیسی نیاز دارد که هنوز ایجاد نشده است. اگر `T13` Migration را ایجاد
می‌کند و `T12` از جدول حاصل استفاده می‌کند، رابطهٔ صحیح چنین است:

> `T13` پیش‌نیاز `T12` است؛ یا `T12` به `T13` وابسته است.

پس باید Migration پیش از Task وابسته قرار گیرد و این رابطه در ترتیب یا Dependencyهای Tasks ثبت
شود. Analyze این ناسازگاری را گزارش می‌کند، اما Taskها را اجرا یا خودکار جابه‌جا نمی‌کند؛ اجرای
ترتیب اصلاح‌شده متعلق به مرحلهٔ Implement است.

#### ۲. مشکل Parallelism

دو Task دارای نشانگر `[P]` باید مستقل و برای اجرای هم‌زمان امن باشند. اگر هر دو فایل مشترکی را
تغییر دهند، این ادعا معتبر نیست؛ زیرا ممکن است Conflict، بازنویسی تغییرات یکدیگر یا کد ناسازگار
ایجاد شود.

این وضعیت الزاماً به معنی وجود Dependency منطقی میان دو Task نیست. ممکن است هیچ‌کدام به خروجی
دیگری نیاز نداشته باشد، اما به‌دلیل تغییر یک منبع مشترک نتوانند هم‌زمان اجرا شوند. راه اصلاح
یکی از این دو است:

- حذف نشانگر `[P]` و تعیین ترتیب اجرای Taskها؛
- بازطراحی مرز Taskها یا فایل‌ها به‌گونه‌ای که تغییرات واقعاً مستقل شوند.

#### ۳. Findingهای مورد انتظار از Analyze

Finding یعنی ایراد یا ناسازگاری مستندی که در بررسی کشف می‌شود، نه خودِ اجرای اصلاح. انتظار
می‌رود Analyze دست‌کم این موارد را گزارش کند:

1. **Dependency/Ordering Finding:** Task وابسته به دیتابیس پیش از Migration قرار گرفته و در
   ترتیب فعلی ممکن است شکست بخورد.
2. **Parallelism Finding:** دو Task با نشانگر `[P]` فایل مشترکی را تغییر می‌دهند و بنابراین
   برای اجرای موازی امن نیستند.

هر Finding مناسب باید محل مشکل، شرح ناسازگاری، اثر احتمالی و پیشنهاد اصلاح را روشن کند.

#### ۴. آیا Coverage صددرصد آمادگی Implement را ثابت می‌کند؟

**خیر.** پوشش ۱۰۰٪ فقط ثابت می‌کند که برای هر Requirement دست‌کم یک Task مرتبط ثبت شده است. این
معیار، وجود رابطه را می‌سنجد؛ نه کیفیت و کفایت آن را.

پیش از Implement باید بررسی شود که Taskها:

- شفاف، دقیق و قابل پیاده‌سازی باشند؛
- تمام رفتار و محدودیت Requirement را واقعاً پوشش دهند؛
- ترتیب و Dependencyهای صحیح داشته باشند؛
- برچسب‌های Parallel معتبر داشته باشند و بر سر فایل یا منبع مشترک تعارض نکنند؛
- با Specification و Plan ناسازگار نباشند.

اگر خود Requirement مبهم باشد، Clarify لازم است؛ اما اگر Requirement روشن و Task ناقص، متعارض
یا بدترتیب باشد، باید Plan یا Tasks اصلاح شود.

#### نتیجهٔ نهایی

Traceability یا پوشش Requirementها شرط لازم است، اما شرط کافی برای شروع Implement نیست. آمادگی
واقعی زمانی به دست می‌آید که علاوه بر Coverage، کیفیت Taskها، ترتیب وابستگی‌ها و ایمنی اجرای
موازی نیز بررسی و اصلاح شده باشند.

## سؤال ۵ — Implement، Validation و Converge

### تحلیل نهایی

#### ۱. آیا Feature کامل و پذیرفته‌شده است؟

**خیر.** موفقیت Build، تکمیل همهٔ Taskهای ثبت‌شده و Pass شدن ۱۲۰ Test شواهد فنی ارزشمندی هستند،
اما کامل‌بودن Feature را به‌تنهایی ثابت نمی‌کنند. در این سناریو دو شکاف قطعی وجود دارد:

- یک قاعدهٔ امنیتی در پیاده‌سازی رعایت نشده است؛
- یک معیار Acceptance انسانی هنوز ارزیابی نشده است.

بنابراین Feature نه کاملاً Validated است و نه Accepted. همچنین «تمام Taskها انجام شده‌اند» فقط
نشان می‌دهد فهرست فعلی Taskها اجرا شده است؛ نه اینکه آن فهرست حتماً کامل بوده یا کد تمام
Requirementها را محقق کرده است.

#### ۲. تفاوت Build، Test، Validation و Acceptance

- **Build:** بررسی می‌کند کد بتواند با ابزارهای پروژه به خروجی قابل اجرا یا انتشار تبدیل شود.
  Build موفق، رعایت منطق کسب‌وکار یا امنیت را تضمین نمی‌کند.
- **Test:** رفتار پیاده‌سازی را در سناریوهایی که برایشان آزمون نوشته شده بررسی می‌کند. Pass شدن
  همهٔ Testها اثبات نمی‌کند که تمام رفتارها، شرایط مرزی و قواعد امنیتی پوشش داده شده‌اند.
- **Validation:** مجموعهٔ شواهد لازم برای اطمینان از تطابق پیاده‌سازی واقعی با Specification،
  محدودیت‌ها و معیارهای کیفی است. Test، Code Review و Security Review می‌توانند بخشی از
  Validation باشند.
- **Acceptance:** تصمیم ذی‌نفع یا مالک واجد صلاحیت دربارهٔ قابل‌قبول‌بودن Feature برای نیاز
  واقعی است. بعضی معیارهای آن به قضاوت انسانی نیاز دارند و Agent نمی‌تواند به‌جای انسان آن‌ها
  را Pass اعلام کند.

> **Test شکست‌خورده** یعنی معیاری اجرا شده و نتیجهٔ آن منفی بوده است؛ اما **Acceptance
> ارزیابی‌نشده** یعنی هنوز هیچ نتیجهٔ Pass یا Fail معتبری نداریم.

برای نمونه، Test می‌تواند وجود پیام خطا را بررسی کند، اما نمایندهٔ کاربران باید قابل‌فهم‌بودن
آن را ارزیابی کند. Test می‌تواند عملکرد دکمه‌ها را بسنجد، اما Product Owner ممکن است لازم باشد
قابل‌استفاده‌بودن کل گردش کار را تأیید کند.

#### ۳. نقش Converge و تفاوت آن با Analyze

- **Analyze** پیش از Implement، اسناد Specification، Plan و Tasks را با یکدیگر مقایسه می‌کند تا
  ناسازگاری، ابهام، نقص پوشش و Dependency نامعتبر را پیدا کند.
- **Converge** پس از شکل‌گرفتن پیاده‌سازی، Codebase واقعی را در برابر Specification، Plan و
  Tasks قرار می‌دهد تا فاصلهٔ میان «آنچه باید ساخته می‌شد» و «آنچه واقعاً ساخته شده» مشخص شود.

در این سناریو، قاعدهٔ امنیتی در کد رعایت نشده است؛ پس Converge باید این شکاف پیاده‌سازی را ثبت
و کار باقی‌مانده را به Task قابل اجرا تبدیل کند. Converge با اعلام اینکه Taskهای قبلی کامل
شده‌اند، شکاف واقعی را نادیده نمی‌گیرد و معیار انسانی را نیز خودکار تأیید نمی‌کند.

#### ۴. مسیر اصلاح شکاف کشف‌شده

مسیر بازگشت به منشأ شکاف بستگی دارد:

- **Specification و Plan درست‌اند، اما کد ناقص است:** Task باقی‌مانده افزوده، توسط Implement
  اجرا و سپس نسخهٔ اصلاح‌شده دوباره ارزیابی می‌شود.
- **Requirement روشن است، اما راه‌حل فنی کافی نیست:** Plan اصلاح می‌شود؛ سپس Tasks و پیاده‌سازی
  به‌روزرسانی می‌شوند.
- **Requirement غایب یا مبهم است:** ابتدا Specify/Clarify انجام می‌شود و تغییرات لازم به Plan،
  Tasks و کد منتقل می‌شوند.
- **Acceptance انسانی باقی مانده است:** یک Manual Acceptance Item یا Gate با مالک انسانی مشخص
  ثبت می‌شود و Feature تا اعلام نتیجه پذیرفته‌شده نیست.

در فرض اصلی که Specification و Plan درست و کامل‌اند و فقط بخشی از پیاده‌سازی جا افتاده است،
زنجیرهٔ مناسب چنین است:

> `Converge Finding → Task جدید → Implement → Build/Test → Validation → Human Acceptance`

در صورت نیاز می‌توان پس از اصلاح، Converge را دوباره اجرا کرد تا باقی‌نماندن شکاف دیگری بررسی
شود.

#### ۵. شرط اعلام نهایی Feature

Feature زمانی قابل اعلام به‌عنوان «کامل و پذیرفته‌شده» است که دست‌کم این شواهد وجود داشته
باشند:

1. Build با موفقیت انجام شده باشد؛
2. Testهای لازم و مرتبط اجرا و Pass شده باشند؛
3. تمام Validationهای لازم انجام شده و تطابق پیاده‌سازی با الزامات را تأیید کرده باشند؛
4. معیارهای Acceptance، به‌ویژه موارد انسانی، توسط مالک واجد صلاحیت بررسی و پذیرفته شده باشند.

عبارت «هیچ Validationای رد نشده» کافی نیست؛ زیرا ممکن است Validation اصلاً انجام نشده باشد.
معیار معتبر این است که **Validationهای لازم تکمیل و موفق شده باشند**.

#### نتیجهٔ نهایی

Build و Test دربارهٔ سلامت فنیِ بخش‌هایی از سیستم شاهد می‌دهند، اما Validation تطابق کل
پیاده‌سازی با الزامات را می‌سنجد و Acceptance تصمیم نهایی صاحب اختیار دربارهٔ قابل‌قبول‌بودن
Feature است. Converge پلی میان اسناد و کد واقعی است: شکاف‌های باقی‌مانده را پیدا می‌کند و آن‌ها
را دوباره وارد چرخهٔ Tasks و Implement می‌کند تا Feature واقعاً—نه فقط روی کاغذ—به وضعیت کامل و
پذیرفته‌شده برسد.
