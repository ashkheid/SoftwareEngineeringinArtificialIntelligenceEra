لاگ مسیر تحلیل سؤال پنجم

این فایل مسیر پرسش‌ها، پاسخ‌ها و تحلیل‌هایی را ثبت می‌کند که به پاسخ نهایی سؤال پنجم می‌رسند.

موضوع: Implement، Build، Test، Validation، Acceptance و Converge

صورت سؤال

Coding Agent گزارش داده است:

«تمام Taskها تکمیل شده‌اند؛ پروژه Build شده و ۱۲۰ Test همگی Passed هستند.»

اما در Code Review متوجه می‌شوید یک قاعدهٔ امنیتی رعایت نشده و یک معیار پذیرش انسانی هنوز ارزیابی نشده است.

  1. آیا Feature قابل اعلام به‌عنوان «کامل و پذیرفته‌شده» است؟
  2. تفاوت Build، Test، Validation و Acceptance چیست؟
  3. Converge در این وضعیت چه نقشی دارد و چه تفاوتی با Analyze دارد؟
  4. اگر Converge شکاف جدیدی پیدا کند، مسیر اصلاح چیست؟

مسیر گفت‌وگو

درخواست کاربر: شروع سؤال پنجم

«بریم سؤال پنجم»

آماده‌سازی مفهومی: چهار ایستگاه متفاوت

گزارش Coding Agent دو شاهد فنی مهم ارائه می‌دهد، اما این شواهد به‌تنهایی کامل‌بودن و پذیرفته‌شدن Feature را ثابت نمی‌کنند:

  • Build: آیا کد می‌تواند به خروجی قابل اجرا یا قابل انتشار تبدیل شود؟ موفقیت Build بیشتر ناسازگاری‌های ساخت و Compilation را رد می‌کند.
  • Test: آیا رفتارهایی که برایشان آزمون نوشته‌ایم مطابق انتظار عمل می‌کنند؟ Passed بودن Testها فقط دربارهٔ چیزهایی شاهد می‌دهد که واقعاً آزموده شده‌اند.
  • Validation: آیا پیاده‌سازی واقعی با Specification، محدودیت‌ها و قواعد مورد انتظار تطابق دارد؟ این بررسی می‌تواند Test، Code Review، Security Review یا ارزیابی‌های دیگر را دربر بگیرد.
  • Acceptance: آیا ذی‌نفع مجاز یا Product Owner، معیارهای پذیرش را بررسی کرده و Feature را برای نیاز واقعی قابل قبول می‌داند؟ بعضی معیارها انسانی‌اند و با Test خودکار اثبات نمی‌شوند.
تمثیل ساده: کارخانه ماشین را بدون خطای مونتاژ ساخته است (Build)؛ آزمون ترمز و چراغ‌ها موفق بوده (Test)؛ بازرس بررسی می‌کند ماشین با همهٔ الزامات ایمنی و سفارش تطابق دارد (Validation)؛ و خریدار تحویل نهایی را بر اساس معیارهای توافق‌شده می‌پذیرد (Acceptance).

پرسش‌های دور اول

  1. با وجود Build موفق و ۱۲۰ Test پاس‌شده، آیا این Feature را «کامل و پذیرفته‌شده» اعلام می‌کنی؟ پاسخ را با اشاره به دو شکاف موجود توضیح بده.
  2. اگر همهٔ Testها پاس شده‌اند ولی قاعدهٔ امنیتی نقض شده، کدام نتیجه دقیق‌تر است؟
    • قاعدهٔ امنیتی مهم نیست؛ چون Testها پاس شده‌اند.
    • Testها فقط موارد نوشته‌شده را پوشش داده‌اند و ممکن است برای این قاعده Test کافی وجود نداشته باشد.
    • Build موفق، رعایت امنیت را خودکار ثابت می‌کند.
  3. به زبان خودت بگو «معیار پذیرش انسانی هنوز ارزیابی نشده» چه تفاوتی با «یک Test شکست خورده» دارد.

پاسخ کاربر — دور اول

  1. خیر؛ چون یک قاعدهٔ امنیتی رعایت نشده و یک معیار پذیرش انسانی هنوز ارزیابی نشده است.
  2. گزینهٔ «ب»: Testها فقط مواردی را بررسی کرده‌اند که برایشان آزمون نوشته شده و ممکن است قاعدهٔ امنیتی پوشش داده نشده باشد.
  3. بعضی موارد لزوماً با Test قابل ارزیابی نیستند. برای نمونه، ممکن است Test برای پاسخ یک سرویس Timeout سی‌ثانیه‌ای داشته باشد، اما انسان بداند سرویس‌های وابسته امروز کند هستند و زمان بیشتری برای پاسخ لازم است؛ درنتیجه Test شکست بخورد ولی بررسی انسانی نتیجه را قابل قبول بداند.

کاربر درخواست کرد برای تفاوت Test و ارزیابی انسانی مثال‌های روشن‌تری ارائه شود.

بازخورد و اصلاح مفهومی: Test شکست‌خورده با Acceptance ارزیابی‌نشده یکی نیست

پاسخ‌های اول و دوم درست‌اند. پاسخ سوم نیز به تفاوت ارزیابی ماشینی و قضاوت انسانی نزدیک است، اما مثال Timeout دو مفهوم جدا را با هم ترکیب می‌کند.

  • Test شکست‌خورده: یک شرط از قبل تعریف‌شده اجرا شده و نتیجهٔ آن منفی بوده است؛ یعنی فعلاً شاهدی علیه رفتار مورد انتظار داریم.
  • Acceptance انسانی ارزیابی‌نشده: هنوز شخص واجد صلاحیت معیار را بررسی نکرده است؛ پس نه نتیجهٔ Pass داریم و نه Fail.

اگر Requirement صراحتاً بگوید «پاسخ باید حداکثر در ۳۰ ثانیه برسد»، کندبودن سرویس وابسته علت شکست را توضیح می‌دهد، اما Requirement را خودکار Pass نمی‌کند. برای Pass کردن باید یکی از این موارد روشن شود:

  • Test در محیط نامعتبر یا مختل اجرا شده و نتیجه‌اش قابل استناد نیست؛
  • Requirement برای شرایط عادی تعریف شده و این اجرا خارج از آن شرایط بوده است؛
  • خود Requirement باید با تصمیم ذی‌نفع مجاز تغییر کند.

انسان نباید یک شکست واقعی را صرفاً با اطلاع از علت آن به Pass تبدیل کند. دانستن علت برای تشخیص و تصمیم‌گیری مفید است، نه برای تغییر معنای معیار.

مثال‌های بهتر برای Acceptance انسانی

  1. قابل‌فهم‌بودن پیام خطا: Test می‌تواند وجود متن و کد خطا را بررسی کند، اما نمایندهٔ کاربران باید قضاوت کند که پیام برای مخاطب واقعی روشن، محترمانه و راهگشاست.
  2. تجربهٔ یک گردش کار: Test ثابت می‌کند همهٔ دکمه‌ها کار می‌کنند؛ Product Owner یا کاربر واقعی ارزیابی می‌کند که فرایند ثبت درخواست گیج‌کننده یا بیش‌ازحد طولانی نیست.
  3. تطابق بصری: بررسی خودکار می‌تواند اندازه یا رنگ را مقایسه کند، اما طراح ممکن است لازم باشد هماهنگی نهایی صفحه با زبان بصری محصول را تأیید کند.
  4. مناسب‌بودن خروجی هوش مصنوعی: Test می‌تواند ساختار پاسخ، نبودن فیلد خالی و محدودیت طول را بررسی کند؛ اما کارشناس حوزه باید مرتبط‌بودن، لحن و کیفیت معنایی پاسخ را بسنجد.

بنابراین عبارت دقیق‌تر این است: بعضی معیارها را می‌توان تا حدی خودکار آزمود، اما پذیرش نهایی آن‌ها به قضاوت انسانی یا اختیار یک ذی‌نفع مشخص وابسته است.

پرسش‌های دور دوم: Analyze در برابر Converge

دو ابزار را در دو زمان متفاوت تصور کن:

  • Analyze: پیش از پیاده‌سازی، Specification، Plan و Tasks را با یکدیگر مقایسه می‌کند تا شکاف‌ها و ناسازگاری‌های اسناد را پیدا کند.
  • Converge: پس از شکل‌گرفتن پیاده‌سازی، کد واقعی را با Specification، Plan و Tasks مقایسه می‌کند تا کارهای باقی‌مانده یا پیاده‌سازی‌های منحرف‌شده را پیدا کرده و به مسیر تکمیل برگرداند.
  1. قاعدهٔ امنیتی در Specification وجود داشته، اما در کد رعایت نشده است. انتظار داری این شکاف را Analyze پیدا کند یا Converge؟ چرا؟
  2. اگر Converge این شکاف را پیدا کند، آیا خودش فوراً کد را اصلاح می‌کند، یا باید ابتدا کار باقی‌مانده به Task مشخصی تبدیل شود و سپس Implement آن را اجرا کند؟
  3. اگر Converge متوجه شود معیار پذیرش انسانی هنوز بررسی نشده، آیا می‌تواند به‌جای انسان آن را Pass اعلام کند؟ چه اقدامی باید ثبت شود؟

پاسخ کاربر — دور دوم

  1. Converge؛ چون عبارت «در کد رعایت نشده» نشان می‌دهد پیاده‌سازی انجام شده و اکنون باید کد واقعی بررسی شود.
  2. به‌نظر کاربر باید دوباره Plan انجام شود، سپس Task تولید شود و بعد Implement اجرا شود.
  3. Converge اجازه ندارد معیار انسانی را به‌جای انسان Pass اعلام کند؛ باید کاری برای عامل انسانی تعریف و به او واگذار شود تا آن را بررسی کند.

بازخورد: مسیر اصلاح به منشأ شکاف بستگی دارد

پاسخ اول درست است: Analyze عمدتاً سازگاری اسناد پیش از Implement را بررسی می‌کند، اما Converge پیاده‌سازی موجود را با Specification، Plan و Tasks می‌سنجد. چون مسئله در کد واقعی دیده شده، این شکاف در قلمرو Converge است.

در پاسخ دوم، بازگشت همیشگی به Plan لازم نیست. باید ابتدا بپرسیم شکاف از کجا آمده است:

  • Specification و Plan درست‌اند، اما کد ناقص است: Converge کار باقی‌مانده را به Task مشخص تبدیل می‌کند؛ سپس Implement آن Task را انجام می‌دهد و نتیجه دوباره Validation می‌شود.
  • راه‌حل فنی یا طراحی کافی نیست: باید Plan یا تصمیم طراحی اصلاح شود؛ بعد Tasks به‌روز و Implement اجرا شود.
  • Requirement غایب یا مبهم است: ابتدا باید به Specify/Clarify برگشت؛ سپس در صورت اثرگذاری، Plan و Tasks نیز به‌روز شوند.
پس در سناریوی فعلی، اگر قاعدهٔ امنیتی از قبل به‌وضوح در Specification و طراحی آمده و فقط پیاده نشده باشد، مسیر کوتاه‌تر چنین است:
Converge → Task جدید → Implement → Validation

پاسخ سوم نیز از نظر مسئولیت درست است: Converge نمی‌تواند جای قضاوت انسان را بگیرد. بااین‌حال بهتر است آن را صرفاً «Task برنامه‌نویسی» ننامیم. می‌توان آن را به‌صورت یک Manual Acceptance Item، مورد Checklist یا Gate با مالک انسانی مشخص ثبت کرد. Feature تا ثبت نتیجه و شواهد این ارزیابی، پذیرفته‌شده محسوب نمی‌شود.

پرسش‌های جمع‌بندی

  1. سه وضعیت زیر را به مسیر درست وصل کن:
    • Requirement امنیتی روشن است و Plan هم راه‌حل را مشخص کرده، ولی کد آن را ندارد.
    • Requirement امنیتی وجود دارد، ولی هیچ تصمیم فنی برای اجرای آن گرفته نشده است.
    • اصلاً معلوم نیست قاعدهٔ امنیتی دقیقاً چه رفتاری می‌خواهد.
    مسیرهای ممکن: بازگشت به Clarify/Specify، بازگشت به Plan، یا ساخت Task جدید و اجرای Implement.
  2. در یک جمله تفاوت Analyze و Converge را با تمرکز بر چیزی که هرکدام مقایسه می‌کنند بیان کن.
  3. برای اعلام نهایی Feature به‌عنوان «کامل و پذیرفته‌شده»، چه چهار شاهد یا نتیجه‌ای باید داشته باشیم؟ از مفاهیم Build، Test، Validation و Acceptance استفاده کن.

پاسخ کاربر — جمع‌بندی

  1. در حالت اول Task ساخته و اجرا می‌شود؛ در حالت دوم به Plan بازمی‌گردیم؛ و در حالت سوم به Clarify/Specify بازمی‌گردیم.
  2. Analyze پیش از پیاده‌سازی، Specification، Plan و Tasks را بررسی می‌کند تا مشکلات را شناسایی کند؛ Converge نیز این سه مورد را پس از پیاده‌سازی بررسی می‌کند تا از کامل‌بودن کار مطمئن شود.
  3. Feature زمانی کامل و پذیرفته‌شده است که Build موفق باشد، همهٔ Testها Pass شده باشند، هیچ Validationای رد نشده باشد و عامل انسانی نیز آن را Accept کرده باشد.

دقیق‌سازی جمع‌بندی

پاسخ اول کاملاً درست است و نشان می‌دهد مسیر اصلاح باید براساس منشأ شکاف انتخاب شود.

پاسخ دوم به یک اصلاح مهم نیاز دارد: Converge فقط همان سه سند را در زمان دیگری با یکدیگر مقایسه نمی‌کند؛ تفاوت اصلی در حضور پیاده‌سازی واقعی است:

  • Analyze: Specification، Plan و Tasks را با یکدیگر مقایسه می‌کند تا پیش از Implement، ناسازگاری و نقص اسناد را پیدا کند.
  • Converge: Codebase و پیاده‌سازی واقعی را در برابر Specification، Plan و Tasks قرار می‌دهد تا شکاف میان «آنچه باید ساخته می‌شد» و «آنچه واقعاً ساخته شده» را کشف کند.

در پاسخ سوم، عبارت «هیچ Validationای رد نشده» کافی نیست؛ چون ممکن است هیچ Validationای اصلاً اجرا نشده باشد و درنتیجه چیزی هم رد نشده باشد. عبارت دقیق این است: تمام Validationهای لازم انجام شده و موفق بوده‌اند.

پس شواهد تکمیل و پذیرش عبارت‌اند از:

  1. Build با موفقیت انجام شده است.
  2. Testهای لازم و مرتبط اجرا و Pass شده‌اند.
  3. Validationهای لازم تکمیل شده و تطابق پیاده‌سازی با الزامات را تأیید کرده‌اند.
  4. معیارهای Acceptance، از جمله موارد انسانی، توسط مالک واجد صلاحیت بررسی و پذیرفته شده‌اند.

آخرین بررسی

فرض کن Converge یک شکاف پیاده‌سازی پیدا کرده و Specification و Plan از قبل درست و کامل‌اند. مسیر را از لحظهٔ کشف شکاف تا امکان اعلام Feature به‌عنوان پذیرفته‌شده، در یک زنجیره بنویس.

پاسخ کاربر — آخرین بررسی

اگر Specification و Plan درست و کامل باشند، احتمالاً راه فنی کافی نبوده است. پیش از بازگشت به Plan باید Build، Test، Validation و Acceptance به‌ترتیب بررسی شوند تا شاید شکاف در این مسیر پیدا شود؛ اگر پیدا نشد، باید دوباره Plan انجام شود.

اصلاح نهایی: کشف شکاف با اصلاح شکاف فرق دارد

در فرض سؤال، Converge شکاف را از قبل پیدا کرده است؛ بنابراین لازم نیست برای یافتن دوبارهٔ همان شکاف، مراحل Build، Test، Validation و Acceptance طی شوند.

همچنین اگر «راه فنی کافی نبوده»، Plan دیگر درست و کامل محسوب نمی‌شود. اما فرض سؤال می‌گوید Specification و Plan درست و کامل‌اند؛ پس مشکل این است که پیاده‌سازی از آن‌ها تبعیت نکرده یا بخشی از کار جا افتاده است.

مسیر مناسب در این حالت چنین است:

Converge Finding → افزودن Task باقی‌مانده → Implement → Build/Test → Validation → Human Acceptance

در صورت نیاز می‌توان پس از اصلاح، Converge را دوباره اجرا کرد تا باقی‌نماندن شکاف پیاده‌سازی تأیید شود.

Build، Test، Validation و Acceptance در این مسیر ابزارهای جست‌وجوی کورکورانه برای شکافی که از قبل شناخته شده نیستند؛ آن‌ها شواهد و Gateهای لازم برای اثبات صحت، تطابق و پذیرش نسخهٔ اصلاح‌شده‌اند.

صورت‌بندی نهایی مورد انتظار

با توجه به اصلاح بالا، زنجیرهٔ درست را یک بار به زبان خودت بنویس. نکتهٔ کلیدی این است که در این سناریو نه Requirement عوض شده و نه طراحی؛ فقط بخشی از پیاده‌سازی باقی مانده است.

تحلیل نهایی

۱. آیا Feature کامل و پذیرفته‌شده است؟

خیر. موفقیت Build، تکمیل همهٔ Taskهای ثبت‌شده و Pass شدن ۱۲۰ Test شواهد فنی ارزشمندی هستند، اما کامل‌بودن Feature را به‌تنهایی ثابت نمی‌کنند. در این سناریو دو شکاف قطعی وجود دارد:

  • یک قاعدهٔ امنیتی در پیاده‌سازی رعایت نشده است؛
  • یک معیار Acceptance انسانی هنوز ارزیابی نشده است.

بنابراین Feature نه کاملاً Validated است و نه Accepted. همچنین «تمام Taskها انجام شده‌اند» فقط نشان می‌دهد فهرست فعلی Taskها اجرا شده است؛ نه اینکه آن فهرست حتماً کامل بوده یا کد تمام Requirementها را محقق کرده است.

۲. تفاوت Build، Test، Validation و Acceptance

  • Build: بررسی می‌کند کد بتواند با ابزارهای پروژه به خروجی قابل اجرا یا انتشار تبدیل شود. Build موفق، رعایت منطق کسب‌وکار یا امنیت را تضمین نمی‌کند.
  • Test: رفتار پیاده‌سازی را در سناریوهایی که برایشان آزمون نوشته شده بررسی می‌کند. Pass شدن همهٔ Testها اثبات نمی‌کند که تمام رفتارها، شرایط مرزی و قواعد امنیتی پوشش داده شده‌اند.
  • Validation: مجموعهٔ شواهد لازم برای اطمینان از تطابق پیاده‌سازی واقعی با Specification، محدودیت‌ها و معیارهای کیفی است. Test، Code Review و Security Review می‌توانند بخشی از Validation باشند.
  • Acceptance: تصمیم ذی‌نفع یا مالک واجد صلاحیت دربارهٔ قابل‌قبول‌بودن Feature برای نیاز واقعی است. بعضی معیارهای آن به قضاوت انسانی نیاز دارند و Agent نمی‌تواند به‌جای انسان آن‌ها را Pass اعلام کند.
Test شکست‌خورده یعنی معیاری اجرا شده و نتیجهٔ آن منفی بوده است؛ اما Acceptance ارزیابی‌نشده یعنی هنوز هیچ نتیجهٔ Pass یا Fail معتبری نداریم.

برای نمونه، Test می‌تواند وجود پیام خطا را بررسی کند، اما نمایندهٔ کاربران باید قابل‌فهم‌بودن آن را ارزیابی کند. Test می‌تواند عملکرد دکمه‌ها را بسنجد، اما Product Owner ممکن است لازم باشد قابل‌استفاده‌بودن کل گردش کار را تأیید کند.

۳. نقش Converge و تفاوت آن با Analyze

  • Analyze پیش از Implement، اسناد Specification، Plan و Tasks را با یکدیگر مقایسه می‌کند تا ناسازگاری، ابهام، نقص پوشش و Dependency نامعتبر را پیدا کند.
  • Converge پس از شکل‌گرفتن پیاده‌سازی، Codebase واقعی را در برابر Specification، Plan و Tasks قرار می‌دهد تا فاصلهٔ میان «آنچه باید ساخته می‌شد» و «آنچه واقعاً ساخته شده» مشخص شود.

در این سناریو، قاعدهٔ امنیتی در کد رعایت نشده است؛ پس Converge باید این شکاف پیاده‌سازی را ثبت و کار باقی‌مانده را به Task قابل اجرا تبدیل کند. Converge با اعلام اینکه Taskهای قبلی کامل شده‌اند، شکاف واقعی را نادیده نمی‌گیرد و معیار انسانی را نیز خودکار تأیید نمی‌کند.

۴. مسیر اصلاح شکاف کشف‌شده

مسیر بازگشت به منشأ شکاف بستگی دارد:

  • Specification و Plan درست‌اند، اما کد ناقص است: Task باقی‌مانده افزوده، توسط Implement اجرا و سپس نسخهٔ اصلاح‌شده دوباره ارزیابی می‌شود.
  • Requirement روشن است، اما راه‌حل فنی کافی نیست: Plan اصلاح می‌شود؛ سپس Tasks و پیاده‌سازی به‌روزرسانی می‌شوند.
  • Requirement غایب یا مبهم است: ابتدا Specify/Clarify انجام می‌شود و تغییرات لازم به Plan، Tasks و کد منتقل می‌شوند.
  • Acceptance انسانی باقی مانده است: یک Manual Acceptance Item یا Gate با مالک انسانی مشخص ثبت می‌شود و Feature تا اعلام نتیجه پذیرفته‌شده نیست.

در فرض اصلی که Specification و Plan درست و کامل‌اند و فقط بخشی از پیاده‌سازی جا افتاده است، زنجیرهٔ مناسب چنین است:

Converge Finding → Task جدید → Implement → Build/Test → Validation → Human Acceptance

در صورت نیاز می‌توان پس از اصلاح، Converge را دوباره اجرا کرد تا باقی‌نماندن شکاف دیگری بررسی شود.

۵. شرط اعلام نهایی Feature

Feature زمانی قابل اعلام به‌عنوان «کامل و پذیرفته‌شده» است که دست‌کم این شواهد وجود داشته باشند:

  1. Build با موفقیت انجام شده باشد؛
  2. Testهای لازم و مرتبط اجرا و Pass شده باشند؛
  3. تمام Validationهای لازم انجام شده و تطابق پیاده‌سازی با الزامات را تأیید کرده باشند؛
  4. معیارهای Acceptance، به‌ویژه موارد انسانی، توسط مالک واجد صلاحیت بررسی و پذیرفته شده باشند.

عبارت «هیچ Validationای رد نشده» کافی نیست؛ زیرا ممکن است Validation اصلاً انجام نشده باشد. معیار معتبر این است که Validationهای لازم تکمیل و موفق شده باشند.

نتیجهٔ نهایی

Build و Test دربارهٔ سلامت فنیِ بخش‌هایی از سیستم شاهد می‌دهند، اما Validation تطابق کل پیاده‌سازی با الزامات را می‌سنجد و Acceptance تصمیم نهایی صاحب اختیار دربارهٔ قابل‌قبول‌بودن Feature است. Converge پلی میان اسناد و کد واقعی است: شکاف‌های باقی‌مانده را پیدا می‌کند و آن‌ها را دوباره وارد چرخهٔ Tasks و Implement می‌کند تا Feature واقعاً—نه فقط روی کاغذ—به وضعیت کامل و پذیرفته‌شده برسد.
