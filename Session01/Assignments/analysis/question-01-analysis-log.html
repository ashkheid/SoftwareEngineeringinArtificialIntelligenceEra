  2. قاعدهٔ جداسازی مسئولیت‌ها باید در Constitution، Plan یا Tasks ثبت شود؟ چرا؟

لاگ گفتگو و تحلیل

مرحلهٔ ۱ — بررسی معنای موفقیت Testها

پرسش: آیا موفق‌شدن Testها فقط رفتارهایی را تأیید می‌کند که واقعاً آزموده شده‌اند و لزوماً نشان نمی‌دهد ساختار کد و مرزبندی لایه‌ها درست است؟

پیشنهاد اولیه: بله؛ مگر اینکه آزمون‌های معماری مستقلی وجود داشته باشند که وابستگی‌ها و محل قرارگیری Business Logic را کنترل کنند.

مرحلهٔ ۲ — پرسش دربارهٔ ماهیت قاعدهٔ معماری

پیشنهاد اولیه: بله؛ چون این قاعده باید در تمام قابلیت‌های فعلی و آینده رعایت شود.

ابهام شناسایی‌شده

هنوز درکی از اتفاقی که افتاده ندارم. چیزی که می‌بینم این است که Agent خودش تصمیم گرفته بخشی از Business Logic را داخل یکی از این بخش‌ها ببرد؛ اما نمی‌دانم این تصمیم درست است یا غلط و اساساً این معماری چیست.

نتیجه: ادامهٔ مصاحبه متوقف شد تا مفاهیم پایهٔ معماری لایه‌ای، Business Logic و مسئولیت Controller روشن شوند.

مرحلهٔ ۳ — توضیح آموزشی معماری

تعریف کاری معماری: معماری در این مسئله یعنی تقسیم مسئولیت میان بخش‌های سیستم و تعیین اینکه هر نوع تصمیم در کدام بخش گرفته شود.

تشبیه رستوران: Controller مانند پیشخدمت است؛ سفارش را می‌گیرد و نتیجه را تحویل می‌دهد. Application و Domain مانند آشپزخانه‌اند؛ قواعد آماده‌سازی و تصمیم‌های اصلی در آنجا اجرا می‌شوند. ممکن است پیشخدمت خودش غذا را درست کند و غذای صحیحی نیز تحویل دهد، اما تقسیم مسئولیت نقض شده است.

لایه مسئولیت اصلی
API / Controller خواندن HTTP Request، استخراج شناسه و کاربر، فراخوانی Use Case و تبدیل نتیجه به HTTP Response
Application اجرای Use Case و هماهنگی جریان عملیات، Repository و Transaction
Domain قواعد اصلی کسب‌وکار، Invariantها و انتقال وضعیت‌ها

نمونه‌هایی از Business Logic در ChangeFlow:

  • فقط Reviewer اجازهٔ تأیید درخواست را دارد.
  • ثبت‌کننده نباید درخواست خودش را تأیید کند.
  • فقط درخواست PendingReview قابل تأیید است.
  • تأیید موفق، وضعیت را به Approved تغییر می‌دهد.

نمونهٔ نامناسب:

Controller:
  request = database.load(id)

  if request.status != PendingReview:
      reject

  if request.requesterId == currentUser.id:
      reject

  request.status = Approved
  database.save(request)

در این حالت رفتار HTTP ممکن است درست باشد و Testها موفق شوند؛ ولی مسیرهایی مانند Message Queue، CLI یا Background Job می‌توانند Controller را دور بزنند و همان قواعد را اجرا نکنند.

شکل مناسب‌تر:

Controller:
  result = approveChangeRequest.execute(id, currentUser)
  return mapResultToHttp(result)

Application / Domain:
  check reviewer permission
  prevent self-approval
  check PendingReview status
  transition request to Approved
  save changes

جمع‌بندی این مرحله: Agent معماری جدیدی انتخاب نکرده است. تیم قبلاً مرز معماری را تعیین کرده بود و Agent با قراردادن قواعد کسب‌وکار در Controller آن مرز را نقض کرده است؛ حتی اگر خروجی قابلیت در Testهای موجود صحیح باشد.

مرحلهٔ جاری — پرسش‌های باز

پرسش باز ۱: آیا اکنون قاعدهٔ زیر را یک قانون پایدار و سراسری پروژه می‌دانیم؟

Controller فقط ورودی و خروجی HTTP را مدیریت کند و تصمیم‌های کسب‌وکار در Application یا Domain گرفته شوند.

در صورت موافقت، باید توضیح داده شود چرا این قانون فقط مخصوص Endpoint تأیید درخواست نیست.

تمرین دسته‌بندی:

  1. خواندن requestId از URL: در انتظار پاسخ
  2. جلوگیری از تأیید درخواست توسط ثبت‌کنندهٔ همان درخواست: در انتظار پاسخ
  3. تبدیل خطای «وضعیت نامعتبر» به HTTP 409: در انتظار پاسخ

درخواست شفاف‌سازی

کاربر درخواست کرد سؤال‌ها با بیان واضح‌تر و مثال ملموس‌تری مطرح شوند.

مرحلهٔ ۴ — بازنویسی ساده‌تر پرسش‌ها

سناریو: کاربری از طریق یک درخواست HTTP می‌خواهد Change Request شمارهٔ 42 را تأیید کند.

  1. عدد 42 داخل URL قرار دارد. کدام بخش باید این عدد را از URL بخواند؟
    • گزینهٔ الف: API / Controller
    • گزینهٔ ب: Application / Domain
  2. سیستم باید بررسی کند که کاربر، ثبت‌کنندهٔ همین Change Request نباشد؛ چون Self-Approval ممنوع است. این بررسی باید در کدام بخش انجام شود؟
    • گزینهٔ الف: API / Controller
    • گزینهٔ ب: Application / Domain
  3. Application یا Domain اعلام می‌کند درخواست به‌دلیل وضعیت نامعتبر قابل تأیید نیست. کدام بخش باید این نتیجه را به پاسخ HTTP با کد 409 تبدیل کند؟
    • گزینهٔ الف: API / Controller
    • گزینهٔ ب: Application / Domain

وضعیت: در انتظار پاسخ کاربر به‌شکل «۱: الف، ۲: ب، ۳: الف» و توضیح دلیل هر انتخاب.

پاسخ کاربر به تمرین دسته‌بندی

  1. خواندن شناسه از URL: گزینهٔ الف، API / Controller
  2. جلوگیری از Self-Approval: گزینهٔ ب، Application / Domain
  3. تبدیل خطا: به‌نظر کاربر Application نتیجه را تبدیل می‌کند و به Controller تحویل می‌دهد.

مرحلهٔ ۵ — بازخورد و تفکیک تصمیم کسب‌وکار از HTTP

پاسخ ۱: درست است. URL بخشی از قرارداد HTTP است؛ بنابراین API / Controller باید شناسهٔ 42 را از آن استخراج کند.

پاسخ ۲: درست است. ممنوعیت Self-Approval یک قاعدهٔ کسب‌وکار است و باید مستقل از روش ورود درخواست، در Application یا Domain اعمال شود.

پاسخ ۳: ایدهٔ کلی نزدیک است، اما عملیات باید به دو مسئولیت تقسیم شود:

  1. Application / Domain نتیجه‌ای مستقل از HTTP مانند InvalidRequestState یا ApprovalNotAllowed تولید می‌کند.
  2. API / Controller آن نتیجه را به پاسخ مخصوص HTTP، برای مثال 409 Conflict، تبدیل می‌کند.

اگر Application مستقیماً کد 409 تولید کند، از HTTP آگاه و به آن وابسته می‌شود. در آن صورت استفاده از همان Use Case از طریق CLI، Message Queue یا یک رابط غیر HTTP دشوارتر خواهد شد.

نتیجهٔ یادگیری: Application دربارهٔ معنای کسب‌وکاری شکست تصمیم می‌گیرد؛ API دربارهٔ نمایش آن شکست در پروتکل HTTP تصمیم می‌گیرد.

تحت هیچ شرایطی هیچ‌کس نباید درخواست خودش را تأیید کند. این قانون مطلق ماست.

مرحلهٔ ۶ — شناسایی Invariant کسب‌وکار

ممنوعیت Self-Approval به‌عنوان یک Invariant کسب‌وکار تثبیت شد: این قانون مستقل از نقش‌های دیگر کاربر، مسیر ورود درخواست و فناوری رابط باید همواره اجرا شود.

در این تحلیل دو قانون متفاوت وجود دارد:

  1. قانون کسب‌وکار: هیچ‌کس نباید درخواست خودش را تأیید کند.
  2. قانون معماری: قواعد کسب‌وکار باید در Application یا Domain اجرا شوند، نه در Controller.

قانون اول می‌گوید سیستم چه رفتاری داشته باشد؛ قانون دوم می‌گوید کد آن رفتار در کدام بخش سیستم قرار بگیرد.

پرسش باز بعدی: آیا قانون معماری دوم نیز باید در تمام Featureهای فعلی و آینده رعایت شود، یا فقط برای عملیات تأیید درخواست است؟

مرحلهٔ ۸ — تفاوت اصول با معماری

اصل یک راهنمای پایدار یا محدودیت برای تصمیم‌گیری است؛ معماری ساختار واقعی حاصل از آن تصمیم‌هاست: اجزا، مسئولیت‌ها، وابستگی‌ها و جریان ارتباط میان آن‌ها.

تشبیه: Constitution مانند ضوابط ساخت‌وساز است؛ معماری مانند نقشهٔ واقعی ساختمان. ضابطه می‌گوید خروج اضطراری الزامی است، ولی نقشه نشان می‌دهد خروجی در کجا و با چه مسیری ساخته می‌شود.

نوع مطلب نمونه محل اصلی ثبت
اصل یا محدودیت پایدار Business Logic نباید به HTTP وابسته باشد. Constitution
ساختار معماری سیستم دارای لایه‌های API، Application، Domain و Infrastructure است و جهت وابستگی‌ها مشخص است. Plan
تصمیم معماری همراه با دلیل انتخاب Modular Monolith به‌جای Microservices یا انتخاب روش Persistence. Research و Plan؛ در پروژه‌های دیگر ممکن است ADR نیز استفاده شود.
جزئیات قرارداد Endpointها، مدل داده و شکل Request و Response. contracts، data-model و Plan
کار اجرایی ایجاد Use Case تأیید و انتقال منطق از Controller. Tasks

Constitution می‌تواند یک قید معماری مشخص را ثبت کند، اما بهتر است به نقشهٔ کامل و پرجزئیات معماری تبدیل نشود. فقط تصمیمی باید وارد Constitution شود که سراسری، پایدار و الزام‌آور باشد و تغییر آن نیازمند بازنگری رسمی اصل پروژه باشد.

در نتیجه، عبارت «Business Logic در Application یا Domain قرار بگیرد» می‌تواند یک اصل معماری در Constitution باشد؛ اما جزئیاتی مانند تعداد پروژه‌ها، نام ماژول‌ها، الگوی Repository یا انتخاب دیتابیس معمولاً در Plan و Research مستند می‌شوند.

تحلیل نهایی

موفق‌شدن Testها و رعایت معماری دو نوع اطمینان متفاوت ایجاد می‌کنند. Testهای رفتاری نشان می‌دهند سیستم در سناریوهای آزموده‌شده خروجی مورد انتظار را تولید می‌کند؛ اما لزوماً بررسی نمی‌کنند این رفتار در کدام لایه پیاده‌سازی شده است. بنابراین ممکن است Controller شامل تمام بررسی‌های وضعیت، مجوز و Self-Approval باشد و Testهای HTTP همچنان موفق شوند. در چنین حالتی رفتار فعلی درست است، ولی ساختار سیستم با تصمیم معماری تیم سازگار نیست.

این تفاوت در توسعه‌های بعدی اهمیت بیشتری پیدا می‌کند. اگر قاعدهٔ «هیچ‌کس نباید درخواست خودش را تأیید کند» فقط داخل Controller قرار بگیرد، مسیری مانند Background Job، CLI یا Message Queue می‌تواند Controller را دور بزند و آن قاعده را اجرا نکند. محل مناسب اجرای چنین قواعدی Application یا Domain است تا رفتار کسب‌وکار مستقل از روش ورود درخواست باقی بماند. Controller باید فقط جزئیات HTTP را مدیریت کند: ورودی را بخواند، Use Case را فراخوانی کند و نتیجهٔ مستقل از HTTP را به Response مناسب، مانند 409 Conflict، تبدیل کند.

محل ثبت قاعدهٔ معماری

قاعدهٔ «Business Logic باید در Application یا Domain قرار بگیرد و API فقط مسئول دریافت درخواست و ارائهٔ پاسخ باشد» یک اصل پایدار و سراسری معماری است؛ بنابراین مرجع اصلی و الزام‌آور آن باید Constitution باشد. بااین‌حال، ثبت آن در Constitution به این معنا نیست که Plan و Tasks نقشی ندارند:

  • Constitution اصل غیرقابل‌چشم‌پوشی و معیار ارزیابی تصمیم‌ها را تعریف می‌کند.
  • Plan نشان می‌دهد Feature مشخص چگونه با ساختار لایه‌ها، جهت وابستگی‌ها و Use Caseها این اصل را رعایت می‌کند.
  • Tasks طراحی را به کارهای اجرایی و قابل پیگیری، مانند ایجاد Use Case و نازک نگه‌داشتن Controller، تبدیل می‌کند.

پس این سه Artifact جایگزین یکدیگر نیستند؛ یک قانون واحد را در سه سطح «حاکمیت»، «طراحی» و «اجرا» قابل ردیابی می‌کنند.

جلوگیری از تکرار مشکل

برای جلوگیری از تکرار این تخلف، اتکا به مستندات به‌تنهایی کافی نیست و باید چند لایهٔ مکمل وجود داشته باشد:

  1. اصل جداسازی مسئولیت‌ها به‌صورت صریح و قابل ارزیابی در Constitution ثبت شود.
  2. Plan هر Feature محل اجرای قواعد کسب‌وکار و مرز لایه‌های درگیر را مشخص کند.
  3. Tasks شامل کارهای صریح برای Application/Domain، Controller و آزمون‌های مربوط به آن‌ها باشد.
  4. Architecture Test یا قوانین وابستگی در CI، وابستگی‌های ممنوع میان لایه‌ها را شناسایی کنند.
  5. Code Review با Checklist بررسی کند که Controller فقط کارهای مربوط به HTTP، فراخوانی Application و نگاشت نتیجه را انجام می‌دهد.

Architecture Test می‌تواند بخشی از تخلف‌ها، مانند وابستگی Domain به API یا Infrastructure، را خودکار تشخیص دهد؛ ولی همیشه قادر نیست معنای یک شرط داخل Controller را بفهمد. به همین دلیل کنترل خودکار باید با بازبینی انسانی تکمیل شود.

نتیجه: سبزبودن Testها برای اعلام صحت رفتار لازم است، اما برای اعلام انطباق کامل کافی نیست. قابلیت زمانی با تصمیم تیم سازگار است که علاوه بر رفتار صحیح، قواعد Constitution، طراحی ثبت‌شده در Plan و مرزهای مسئولیتی نیز رعایت شده باشند.
